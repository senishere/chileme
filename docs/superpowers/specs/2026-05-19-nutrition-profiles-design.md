# 营养扩展与本地档案设计

日期：2026-05-19

## 目标

本轮升级把“吃了么”从单一记录账本扩展为支持本地档案、膳食纤维和包装营养表手动录入辅助的版本。它继续保持本地优先，不接真实 AI 服务，不做云同步，不改变食物库共享的基本体验。

本轮采用“基础升级 + 必要拆边界”的方案：实现明确可用的本地功能，同时把过大的 `src/app.js` 拆成更容易继续扩展的视图和 UI 模块。未来拍照识别营养成分表和拍照识别食物可以接入预留接口，但任何识别结果都必须由用户确认后才进入食物库或记录。

## 范围

包含：

- 膳食纤维字段，统一按每 `100g` 食物录入。
- 每条记录按数量计算膳食纤维。
- 今日结构显示膳食纤维进度和状态。
- 记录明细导出包含膳食纤维。
- 食物表单支持 `kJ / 100g` 辅助输入，并换算为内部 `kcal`。
- 本地档案/阶段，记录和目标按档案隔离，食物库共享。
- 完整备份 JSON 支持所有档案。
- 预留 LLM 识别接口和结果结构，但不做真实调用和可见 AI 按钮。
- 拆分 `src/app.js` 的视图、格式化、图片处理和识别接口边界。

不包含：

- 真实拍照识别营养成分表。
- 真实拍照识别食物。
- 估重算法。
- 用户登录、云同步、多设备合并。
- 包装营养的每份或每包装换算 UI。本轮仍只接受每 `100g` 营养。
- 统计页新增膳食纤维趋势。

## 数据模型

### Nutrition

营养字段增加 `fiber`，单位为 `g`。

```json
{
  "calories": 116,
  "protein": 2.6,
  "carbs": 25.9,
  "fat": 0.3,
  "sodium": 1,
  "fiber": 0.3
}
```

规则：

- `calories` 继续表示 `kcal`。
- `fiber` 用于食物、记录 item、每日汇总、今日结构和明细导出。
- 旧数据缺少 `fiber` 时补 `0`。
- 内部不存 `kilojoules`，`kJ` 只作为录入时换算来源。
- 换算公式：`kcal = kJ / 4.184`。
- 换算结果使用现有营养数值精度规则保留两位小数。

### Food

食物继续共享在顶层，营养仍统一为每 `100g`。

```json
{
  "id": "food_rice",
  "name": "米饭",
  "category": "细粮",
  "icon": "🍚",
  "image": "",
  "nutritionPer100g": {
    "calories": 116,
    "protein": 2.6,
    "carbs": 25.9,
    "fat": 0.3,
    "sodium": 1,
    "fiber": 0.3
  },
  "quickAdd": true
}
```

新增或编辑食物时，用户可以填写：

- `热量 kcal / 100g`
- `千焦 kJ / 100g`
- `蛋白质 g / 100g`
- `碳水 g / 100g`
- `脂肪 g / 100g`
- `钠 mg / 100g`
- `膳食纤维 g / 100g`

如果 `kcal` 为空且 `kJ` 有值，保存时用 `kJ / 4.184` 生成 `calories`。如果 `kcal` 和 `kJ` 都有值，以 `kcal` 为准，不自动覆盖用户输入。

### LocalProfile

“分用户记录”在本轮定义为本地档案或阶段。它表示同一个人在不同阶段的记录账本，例如“日常维持”“减脂期”“出差期”。档案隔离记录和目标，但共享食物库、分类、自定义食物和默认食物。

```json
{
  "id": "profile_default",
  "name": "日常维持",
  "profile": {
    "sex": "female",
    "age": 30,
    "heightCm": 165,
    "weightKg": 60,
    "activityLevel": "light",
    "goal": "maintain"
  },
  "dailyGoal": {
    "calories": 2000,
    "protein": 100,
    "waterMl": 2000,
    "fiber": 25
  },
  "entries": [],
  "waterEntries": []
}
```

顶层状态调整为：

```json
{
  "activeProfileId": "profile_default",
  "profiles": [],
  "categories": [],
  "foods": []
}
```

旧状态没有 `profiles` 时，迁移创建一个默认档案，并把旧的 `profile`、`dailyGoal`、`entries` 和 `waterEntries` 搬入该档案。

## 页面设计

### 今天

今日页只显示当前档案的数据。

- 顶部显示当前档案名称。
- 今日汇总读取当前档案的 `entries` 和 `waterEntries`。
- 今日结构增加“膳食纤维”，展示进度条和状态。
- 快捷添加仍使用共享食物库。
- 记录食物时默认写入当前档案，不在记录弹窗里重复选择档案。

膳食纤维状态沿用营养目标的比例状态：

- `< 40%`：严重不足
- `40%-75%`：不足
- `75%-105%`：正常范围
- `105%-120%`：偏高
- `> 120%`：超量

### 食物

食物页仍管理共享食物库。

- 新建/编辑食物表单增加 `kJ / 100g` 和 `膳食纤维 / 100g`。
- 保存时只持久化 `nutritionPer100g.calories`，不持久化 `kJ`。
- 如果用户只填了 `kJ`，显示和记录都使用换算后的 `kcal`。
- 不放“拍照识别食物”按钮，避免出现不可用入口。

### 设置

设置页增加档案区。

能力：

- 选择当前档案。
- 新增档案。
- 重命名档案。
- 删除档案。
- 至少保留一个档案。

个人基础资料和每日目标编辑当前档案。完整备份 JSON 导出所有档案和共享食物库。最近 7 天或 30 天明细导出只导出当前档案。

### 识别预留

本轮只增加代码接口，不显示不可用 AI 按钮。

未来识别营养成分表的结果目标是生成可确认的食物草稿：

```json
{
  "source": "nutrition_label",
  "foodName": "包装食品",
  "basis": "per100g",
  "nutritionPer100g": {
    "calories": 0,
    "protein": 0,
    "carbs": 0,
    "fat": 0,
    "sodium": 0,
    "fiber": 0
  },
  "notes": [],
  "confidence": 0.8
}
```

未来识别食物照片的结果目标是生成候选项，不估重：

```json
{
  "source": "food_photo",
  "candidates": [
    {
      "name": "米饭",
      "matchedFoodId": "food_rice",
      "confidence": 0.7,
      "note": "需要用户输入克数"
    }
  ]
}
```

识别接口不直接写入状态。调用者必须把结果展示给用户确认，再保存为食物或记录。

## 模块拆分

保持 vanilla JavaScript，不引入框架。

- `src/app.js`：启动、全局状态、路由、事件绑定。
- `src/views/today.js`：今日汇总、今日结构、快捷添加、时间线。
- `src/views/foods.js`：食物列表、食物表单、分类管理。
- `src/views/stats.js`：统计视图。
- `src/views/settings.js`：设置、档案管理、导入导出入口。
- `src/ui/format.js`：数字、时间、HTML escape、单位标签、kJ/kcal 换算显示辅助。
- `src/ui/image.js`：照片读取、压缩和 data URL 尺寸控制。
- `src/recognition.js`：未来 LLM 识别接口、输入输出结构和未配置错误。

拆分原则：

- `domain.js` 继续负责纯计算、数据模型、汇总、导出行和档案辅助函数。
- `store.js` 继续负责 normalize、迁移、完整备份导入导出和 localStorage。
- 视图模块只生成 HTML 和少量视图级辅助，不直接访问 `localStorage`。
- 状态修改通过集中 handler 完成，避免视图模块散落写状态。

## 迁移

旧状态迁移规则：

1. 如果存在 `profiles`，规范化所有档案，确保至少一个有效档案。
2. 如果不存在 `profiles`，创建默认档案：
   - `id: "profile_default"`
   - `name: "日常维持"`
   - `profile` 来自旧顶层 `profile`
   - `dailyGoal` 来自旧顶层 `dailyGoal`
   - `entries` 来自旧顶层 `entries`
   - `waterEntries` 来自旧顶层 `waterEntries`
3. `activeProfileId` 缺失或无效时，使用第一个档案。
4. 旧食物和旧记录 item 的营养补 `fiber: 0`。
5. 共享 `categories` 和 `foods` 继续沿用当前默认合并和用户数据保护规则。
6. 旧完整备份 JSON 可导入，新完整备份 JSON 可导出。

明细 JSON/CSV 仍只用于查看和外部分析，不作为完整恢复路径。

## 错误处理

- `kJ` 输入必须是非负数字，空值视为未填写。
- `kcal` 和 `kJ` 都为空时，热量保存为 `0`。
- 删除档案需要确认。
- 只有一个档案时不允许删除。
- 删除当前档案后，自动切换到剩余第一个档案。
- 导入备份后重新规范化，并确保当前档案存在。
- 未来识别接口未配置时应返回明确错误，不吞掉失败。
- 识别结果永远不能自动写入食物库或记录。

## 测试

### Domain

- `kJ` 转 `kcal`。
- `fiber` 参与食物营养计算。
- 今日汇总包含 `fiber`。
- 今日结构包含 `fiber`。
- 当前档案记录隔离。
- 多档案辅助函数选择、创建、重命名和删除。

### Store

- 旧状态迁移成默认档案。
- 多档案状态 normalize 后仍隔离记录。
- 旧食物补 `fiber: 0`。
- 旧记录 item 补 `fiber: 0`。
- 无效 `activeProfileId` 自动修复。
- 旧备份和新备份都可导入。

### PWA / UI Contract

- 食物表单包含 `kJ / 100g` 和 `膳食纤维 / 100g` 输入。
- 设置页包含档案选择、新增、重命名和删除入口。
- 今日页显示当前档案名称。
- 不出现不可用的 AI 识别按钮。

### Manual Smoke

- 新增“减脂期”档案，记录一条食物，切回“日常维持”后看不到这条记录。
- 新建食物只填写 `kJ / 100g`，保存后记录显示换算后的 kcal。
- 新建含膳食纤维的食物并记录，今日结构显示纤维进度。
- 导出完整备份后重新导入，所有档案和共享食物库保留。

## 接受标准

- 旧用户数据自动迁移，不丢失记录、饮水、目标、食物和分类。
- 食物库在档案之间共享。
- 每个档案的记录、饮水、个人资料和每日目标相互隔离。
- `fiber` 在食物、记录、今日汇总、今日结构和明细导出中一致。
- `kJ` 只作为录入辅助，不进入持久数据模型。
- 真实 AI 识别不在本轮暴露给用户。
- `npm test`、`TZ=America/Los_Angeles npm test`、`node --check` 和 `git diff --check` 通过。
